# HandOffly Mobile (PWA)

A compact, installable, phone-first app for HandOffly. It is **a separate frontend**: it shares no code, build, dependencies or scripts with `frontend/` (customers, desktop) or `support-portal/`, and it talks to the **same backend and database** through the existing `/api/v1` endpoints. All business rules (the handoff state machine, return arithmetic, subscription limits, permissions) stay in the backend; this app only shows what the backend says and sends what the person types.

## What it does (v1)

| Area | What you can do |
|---|---|
| Sign in | Email + password through the existing login; the session is the backend's JWT (a 401 clears it and returns to sign-in). No registration here. |
| Handoffs (dashboard) | Needs-attention cards (Overdue, Awaiting recipient), search, status filters with counts, handoff cards with Given / Returned / Missing / Remaining, "Load more". |
| New handoff | Details, recipient, item cards (name, quantity, unit; condition / ID / notes under "More"), **Save draft** or **Save & send link**, **Duplicate** (`/new?from=<id>` uses the backend's template). Edit a draft. |
| Handoff detail | Status, dates, quantity tiles, items, return history, missing-item notices, documents (Proof-of-Handoff PDF, attachments), event history. Actions come from the backend's `availableActions`: send, resend link, record return, confirm a return, request missing confirmation, close (reason required when items are missing), mark disputed, cancel, delete draft (the draft leaves your lists; its history is kept by the backend). |
| Record return | Manual only: tick items, **Return qty**, **Condition**, **Missing**, **Note**. "Still with recipient" = Remaining − Return − Missing is shown live and a partial return never marks the rest missing. |
| Recipient link | `/r/:token` (public, one handoff per token): review items and documents, **Accept & acknowledge** / **Decline**, confirm missing items, ask to wait for the return. Wording is a *typed acknowledgement*, never an e-signature. |
| Account | Plan and validity, edit your details, change password (the backend ends your other sessions), light / dark / match-phone theme, sign out. |

| Reports | **Handoff list** (period, status filter, sort, paging, **Export CSV**) and **Summary** totals, through the existing report endpoints; **Ask AI** (the AI Report Assistant, plans that include HandoffCheck). Opened from the top bar. An ended plan is told so (the backend refuses reports without an active plan). |

**Not in v1** (deliberately): HandoffCheck, Jobs / Job History, importing items from a file, attachment upload, support tickets, registration, payments. They are not bypassed — they simply are not offered.

## PWA

- Web manifest (`HandOffly`, standalone, brand blue `#2563eb`, 64 / 192 / 512 px and maskable icons), Apple touch icon, `theme-color`.
- Service worker generated by `vite-plugin-pwa` (Workbox `generateSW`, `autoUpdate`). It **precaches only the built app shell** (HTML, JS, CSS, icons, manifest). `/api` is never given to it: there is no runtime caching, so no API response, handoff, recipient page, PDF or attachment is ever stored. After sign-out nothing private exists in any cache.
- Offline: the shell opens and says **"Can’t reach HandOffly"** (you stay signed in; *Try again* re-checks). An offline banner says that nothing is saved on the phone. **There is no offline creation, return recording or sync.**
- Icons are generated from `public/favicon.svg` with `npm run generate-icons` (the existing apps have no brand image assets to reuse).

Install: open the app in Chrome / Edge (Android) → menu → *Install app*, or Safari (iOS) → Share → *Add to Home Screen*. (A service worker needs HTTPS or `localhost`.)

## Run locally

Needs Node **^20.19 or ≥22.12** (Vite 8). The backend runs as usual (`http://localhost:8080`).

```bash
cd mobile-pwa
npm install
npm run dev            # http://localhost:5180
```

`/api` is proxied to the backend (`VITE_DEV_API_TARGET`, default `http://localhost:8080`), so the browser stays on one origin and **no CORS configuration is needed**. The proxy drops the `Origin` header so the backend does not treat the call as cross-origin (the backend only lists the other apps' origins).

Dev port **5180** (the other apps use 5173 / 5175; backend 8080).

## Build and deploy

```bash
npm run build          # tsc -b && vite build  → dist/
npm run preview        # serves dist/ on :4180 with the same /api proxy
npm test               # vitest: return-quantity rules, and component tests (jsdom) for sign-in, the form, navigation, the dashboard and Reports
npm run lint           # tsc -b --noEmit
```

Serve `dist/` as static files over **HTTPS**, with a single-page fallback to `index.html`. Two ways to reach the API:

1. **Same origin (recommended, no backend change).** Put the app and the API behind one host; pass `/api/` to the backend and leave `VITE_API_BASE_URL` unset:

   ```nginx
   location /api/ { proxy_pass http://backend:8080; }
   location = /sw.js { add_header Cache-Control "no-cache"; try_files $uri =404; }
   location / { try_files $uri /index.html; }
   ```

2. **Separate origin.** Build with `VITE_API_BASE_URL=https://api.example.com npm run build`, and the backend must be started with this app's origin in its **existing** environment setting:

   ```
   CORS_ALLOWED_ORIGINS=https://app.example.com,https://m.example.com
   ```

   Without it the backend rejects the browser's preflight (checked: an origin that is not listed gets `403`, a listed one gets the CORS headers). Nothing in the backend code needs to change.

Optional: recipient emails link to `RECIPIENT_LINK_BASE_URL` (default the desktop app's `/r`). Point it at this app's `/r` if recipients should open their link here; the recipient page works in either app.

`.env.example` lists the two optional variables. No secrets belong in this app; the only thing it stores in the browser is the session token (`handoffly.mobile.token`) and the theme choice. Passwords are never stored.

The look is documented in [`DESIGN.md`](DESIGN.md): tokens, components and rules for new screens.

## How it is built

```
mobile-pwa/
  index.html  vite.config.ts  pwa-assets.config.ts  tsconfig.json  package.json  package-lock.json  .env.example
  public/                  favicon.svg, favicon.ico, pwa-*.png, maskable-icon-512x512.png, apple-touch-icon-180x180.png
  src/
    main.tsx App.tsx styles.css
    api/        client.ts (base URL, token, 401 handling, network errors, downloads)  endpoints.ts  types.ts
    auth/       AuthContext.tsx
    lib/        format.ts  quantity.ts (+ .test.ts)  theme.ts  useTransient.ts
    components/ AppShell.tsx (top bar, bottom nav, offline banner)  ConfirmSheet.tsx  HandoffForm.tsx  HandoffCard.tsx  Icon.tsx
                ReportAssistantSheet.tsx  ui.tsx
    test/       setup.ts  utils.tsx
    pages/      LoginPage  DashboardPage  NewHandoffPage  EditHandoffPage  HandoffDetailPage  ReturnPage  RecipientPage  ReportsPage  AccountPage
```

Result messages ("Draft saved.", "Return recorded.") clear themselves after 5 seconds (`useTransient`); load failures stay until retried. A confirmation sheet is closed only by its own buttons or Escape, never by a tap outside it.

### Backend endpoints used (all existing)

`POST /auth/login`, `GET|PUT /auth/me`, `POST /auth/change-password`; `GET /handoffs`, `/handoffs/dashboard`, `/handoffs/{id}`, `/handoffs/{id}/template`; `POST /handoffs`, `PATCH /handoffs/{id}`, `PUT /handoffs/{id}/items`, `DELETE /handoffs/{id}`; `POST /handoffs/{id}/{submit|resend-link|cancel|dispute|close|request-missing-confirmation}`; `GET /handoffs/{id}/pdf`, `/handoffs/{id}/attachments/{aid}/content`; `POST /handoffs/{id}/returns`, `/handoffs/{id}/returns/{rid}/confirm`; `GET /r/{token}`, `POST /r/{token}/{accept|reject|confirm-missing|request-return-wait}`, `GET /r/{token}/attachments/{aid}/content`; `GET /reports/handoffs`, `/reports/handoffs/export`, `/reports/assistant/suggestions`; `POST /reports/assistant/ask`.

The only logic mirrored on the phone is the live "Still with recipient" figure and the matching pre-send check (`src/lib/quantity.ts`, unit-tested against the backend's documented rules); the backend re-checks every request and is what refuses a bad one. Subscription limits are never enforced here: the screens warn early from `user.subscription`, and the backend answers `403 subscription_expired` / `no_active_subscription`.

## Known limits

- The Overdue filter narrows the list the backend returns (its list endpoint has no overdue filter), so it keeps loading more pages until it has some to show.
